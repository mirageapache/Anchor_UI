# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`@anchor-ui/core` — a framework-agnostic Web Component library built with Lit 3 + TypeScript, styled by SCSS design tokens exposed as CSS custom properties. Published as ESM-only. Elements use the `aui-` prefix (`<aui-button>`, `<aui-tooltip>`, …). Docs/specs live in `doc/` (written in Traditional Chinese): `anchor-ui-spec.md`, `design-system.md` (token dictionary), `anchor-ui-components-list.md` (20 planned components), `anchor-ui-development-schedule.md` (phases / TASK-xxx ids referenced in commit messages).

Merging the release PR makes release-please tag the merge commit (lightweight tag via `force-tag-creation`) and create a **draft** Release, then call `.github/workflows/release.yml` (`workflow_call`, also `workflow_dispatch` with a `tag` input for reruns; tags created by `GITHUB_TOKEN` trigger nothing): it checks the tag is on `main`, waits for that commit's required checks (read from the `main` Ruleset by `scripts/wait-for-ci.mjs --sha`), runs `pnpm release:pack` with `RELEASE_TAG` (read by `scripts/verify-release.mjs` for the tag/version check; the tarball comes from `scripts/pack.mjs`, which packs a staged copy whose `package.json` has install lifecycle scripts such as `prepare: husky` removed), and uploads it as an artifact; a separate `publish` job (the only one with `contents: write`; no checkout, no install) attaches the tarball and publishes the Release (prerelease when the version contains `-`). A release that is already published is not overwritten unless the `overwrite-published` input is set (a rebuilt tarball has different bytes). A final job merges `main` back into `develop`. `"prerelease": true` (versioning `prerelease`, type `beta`) stays on permanently, so computed versions are always `x.y.z-beta(.n)`; a stable release comes only from a `chore(release): …` commit with a `Release-As: <version>` footer (it overrides the versioning strategy and only applies until that release; an empty commit is fine). `v0.3.0` was the first release made by release-please. release-please opens no release PR when the changelog would be empty (`No user facing commits found`): only `feat`, `fix`, `perf`, `revert` and `chore(release)` (a scoped visible section) are listed, so the `Release-As` commit must be `chore(release): …`, and the `sync-develop` merge message deliberately is not a Conventional Commit so it never shows up in the next changelog. release-please also parses merge-commit bodies, and GitHub's "Default message" puts the PR title there (the ideal `MERGE_MESSAGE` + `BLANK` combination is rejected by GitHub with `invalid_merge_commit_setting_combo`; the other two options put the PR title in the merge commit title), so develop → main PR titles must not be Conventional Commits (e.g. `合併 develop：…`) and are merged with a merge commit, not squash — otherwise the entry is listed twice. `CHANGELOG.md` is in `.prettierignore` to keep release-please's format. `v0.3.0-beta` and earlier were released by hand with annotated tags.

**CI** (`.github/workflows/ci.yml`, PRs to `main` and `develop`, pushes on `main`, plus `workflow_dispatch` for manual reruns, which do not count toward PR required checks): the lint job (incl. `check:versions`, `audit:runtime`, `release:verify --all-tags` and actionlint via the `rhysd/actionlint` Docker image — workflows can only really be exercised on GitHub, so lint them) gates the parallel `build`, `size-report`, `storybook`, `visual` and `test` jobs; `build` also packs the tarball and uploads it as an artifact for the `smoke` matrix job (`Framework Smoke Test (vue3)` / `(angular)` / `(react)`, needs only Node + npm) and the `smoke-ssr` job (`Framework Smoke Test (angular-ssr)`, runs in the Playwright image because it needs Chromium); all four names must be in the `main` Ruleset to gate merges and releases; a final `CI Time Budget` job (`scripts/ci-time-report.mjs`, `actions: read`) writes per-job durations to the job summary and emits a warning (never a failure) when the run exceeds the 8-minute PR budget of TASK-214. Superseded PR runs are cancelled via `concurrency`. The workflow token defaults to `contents: read` and checkouts use `persist-credentials: false` (CI runs PR code and dependency build scripts); jobs that need more declare their own `permissions` (`size-report` hands a `pull-requests: write` token to `andresz1/size-limit-action`, which builds the PR head: an accepted trade-off of the same kind as the preview deploy — same-repo PRs only, forks get a read-only token). **Storybook preview** (`.github/workflows/storybook-preview.yml`, TASK-308): PRs to `main` build Storybook and deploy it to the `gh-pages` branch under `pr-preview/pr-<n>/`, then post or update one PR comment with the link (found by a hidden marker); closing the PR removes the directory (the `cleanup` job is triggered by `pull_request_target` so it also runs for conflicted PRs and executes `main`'s scripts, never PR code); pushes to `main` deploy to the site root and keep `pr-preview/`. ## Architecture

**Component layout** — each component is a folder `src/components/<name>/` with `<name>.ts` (LitElement class), `<name>.styles.ts` (`css` tagged template), `<name>.types.ts`, `index.ts` (re-exports class + types), `<name>.test.ts`, `<name>.a11y.test.ts`. A new component must also be exported from `src/components/index.ts` (which `src/index.ts` re-exports), get its `package.json` `exports` / `sideEffects` entries regenerated with `pnpm sync:package` (from `scripts/components.mjs`, the single source of the component list; the defining module must be named `<name>.ts`), a size baseline in `.size-limit.mjs` `BASELINES`, and gets a story in `src/stories/`. If it imports another component (e.g. icon-button → tooltip), add that edge to `ALLOWED_COMPONENT_DEPS` in `scripts/verify-package.mjs` — the tree-shaking check uses this explicit allow-list (not the source imports) and also inspects bundled modules, so undeclared cross-component code fails. `pnpm verify:package` and `pnpm size` fail if any of these are missing. Vite picks up the build entry automatically. Keep `"./src/**/*.ts"` in `sideEffects`: the field also applies to the library's own build, and without it bare registration imports such as `import '../tooltip/index.js'` get tree-shaken out of `dist/`.

**Tokens** — `src/tokens/*.scss` is the single source of truth (colors, typography, spacing, radius, motion). It is compiled two ways: into `dist/tokens.css` via `build:tokens` (sass), and also exposed as source SCSS through package exports (`./tokens`, `./reset`). Component styles reference tokens via `var(--space-lg, 24px)` with literal fallbacks; they never hardcode theme values.

**Theming** — dark mode is driven by `data-theme="dark"` on `<html>`. `setTheme` / `getTheme` / `toggleTheme` in `src/index.ts` manage it and briefly add a `.theme-transitioning` class for smooth transitions.

**Build** — Vite library mode, ESM-only with `preserveModules` (output mirrors `src/`): a full entry `src/index.ts` (registers every component) plus one entry per `src/components/*/index.ts`, exposed as `@anchor-ui/core/<name>` for tree-shakable on-demand imports. `lit*` and `@floating-ui/*` are externalized (`@floating-ui/dom` is a runtime dependency); test, story and `test-utils` files are excluded from the `.d.ts` output. `__PKG_VERSION__` is injected from `package.json` via Vite `define` (declared in `src/env.d.ts`). `@` aliases `src/`.

**Tooltip** is the most involved component: native Popover API (top layer) + `@floating-ui/dom` (`computePosition`/`autoUpdate`/flip/shift/arrow), emits cancelable `aui-show`/`aui-hide` and `aui-after-show`/`aui-after-hide` events. While open it sets `aria-describedby` on its target; for `<aui-button>` the focusable element is the inner `<button>`, so Button resolves its host `aria-describedby` and hands the elements over via `ariaDescribedByElements` (verify with `getAxNode` on the inner element; besides `role` / `name` / `description` it returns the computed ARIA `properties`, e.g. `expanded`, `hasPopup`, `modal`). Custom events are prefixed `aui-`.

**Popover** — `<aui-popover>` (TASK-505) is the click-triggered, non-modal counterpart of Tooltip for interactive content: the `trigger` slot holds the trigger, the default slot the panel content; the panel is a `role="dialog"` `popover="manual"` element positioned by `@floating-ui/dom`, named by `label` or, without one, by the trigger through `ariaLabelledByElements` (element references may point into an ancestor tree, IDREFs can't leave the shadow root). Cancelable `aui-show` / `aui-hide` are dispatched in `willUpdate`, so a cancelled open or close is folded into the same render (no change-in-update, no reflected `open` flicker); reopening during the exit transition first finishes the interrupted close (`aui-after-hide`, popover hidden) so the events stay paired. Opening (not when rendered `open`) moves focus to the first focusable slotted element (`autofocus` first, awaiting its `updateComplete` like Modal; custom elements are tried with `focus()` and kept if they end up `:focus-within`; content of nested overlays — another popover's panel, Modal, Drawer, Alert — is skipped), falling back to the panel. Close reasons (`aui-hide` / `aui-after-hide` `detail.reason`): `trigger`, `escape` (keydown on the host, `preventDefault` so an enclosing modal stays open), `outside` (document `pointerdown`; focus goes back to the trigger only if it was inside the popover at pointerdown and ended up on `<body>`), `focus-out` (no focus move), `api` (also on removal while open, non-cancelable). The trigger's `aria-expanded` / `aria-haspopup` / `aria-controls` (pointing at the popover host) go through `src/internal/popup-trigger.ts`: `<aui-button>` and `<aui-icon-button>` implement the `POPUP_TRIGGER` symbol method and render the state on their inner `<button>` (ARIA states on the role-less host would be ignored and flagged by axe); other triggers get plain attributes, and the values they had before are restored on release. `src/internal/floating.ts` holds the placement → transform-origin map shared with Tooltip. Subclasses (Dropdown Menu) override `popupRole`, `focusPanel()` and use `close(reason)`. Dispatch events with literal names: the manifest analyzer turns `new CustomEvent(variable)` into an event named after the variable, which `generate-framework-types.mjs` now rejects.

**Menu** — `<aui-menu>` (TASK-506) extends `AuiPopover` (`popupRole = 'menu'`, so the trigger gets `aria-haspopup="menu"`; `menu → popover` is in `ALLOWED_COMPONENT_DEPS`; Popover's `static styles` is typed `CSSResultGroup` so the subclass can append `menuStyles`). Items are the panel's direct slotted children (not a custom element, so the one-tag-per-entry check holds): on `slotchange` (and a `MutationObserver` for `disabled`) they get `role="menuitem"` (a user's `menuitemcheckbox` / `menuitemradio` is kept), `tabindex="-1"`, `type="button"` for `<button>` without a type (so a menu inside a `<form>` does not submit it) and `aria-disabled` derived from the original value plus native `disabled`; `<hr>` becomes a separator. The original values of these attributes are recorded per element and restored when the element leaves the menu. WAI-ARIA Menu Button keyboard: ↓ / ↑ on the trigger opens and focuses the first / last item (Enter / Space open through the native click; the ↑ flag is cleared after the update so a cancelled open does not leak), inside the menu ↑ ↓ wrap, Home / End, single-character type-ahead on `aria-label` or text (IME input sends `Process` and is not supported), Tab / Shift+Tab close; the pointer moves focus to the hovered item. Selection always goes through one click listener that dispatches cancelable `aui-select` (`detail.item`, `detail.value` = `value` attribute or text) and closes with reason `select`: Enter on a native `<button>` / `<a href>` is left to the browser (keeps Shift+Enter etc.), other Enter and every Space are prevented and call `item.click()`. Keys from editable elements and clicks from other interactive elements inside an item are ignored (no submenus). `aria-disabled` items stay focusable but are not selectable (APG); natively `disabled` items can't take focus and are skipped. The active item is found with `:focus-within` (focus may be inside an item's shadow root, and items may be re-slotted from another component); `focusPanel` awaits a Lit item's `updateComplete` like the base class.

**Breadcrumb** — `<aui-breadcrumb>` (TASK-507) takes its levels as data (`items: { label, href? }[]`, like Footer's `columns`) because the `<nav aria-label>` / `<ol>` / `<li>` structure must be generated inside its shadow root; the last level is the current page (`aria-current="page"`, still a link when it has an `href`), `href` goes through `safeHref`, separators are `aria-hidden`. The list is laid out inline, so the templates of `<ol>` / `<li>` are kept on one line with `// prettier-ignore` (whitespace between inline elements would render as extra spaces); the spaces inside the separator are the intended line-break points, and `word-break: keep-all` keeps CJK names whole. Chromium's CDP accessibility tree does not expose `aria-current`, so tests check the attribute. `<aui-header>` has a `breadcrumb` slot above the tags (it does not import Breadcrumb).

**Form controls** — `<aui-input>` and `<aui-segmented>` are form-associated custom elements sharing `src/internal/form-control.ts` (`FormControlController`: `attachInternals`, synchronous `setFormValue`, and the hidden-input + `reset`-listener fallback when `attachInternals` is missing, e.g. happy-dom). For `<aui-input>`: `setFormValue` runs synchronously on every value change, validity is mirrored from the inner native `<input>`/`<textarea>` (the single source of truth, incl. `setCustomValidity`) into `ElementInternals`, and it implements `formResetCallback` / `formDisabledCallback` / `formStateRestoreCallback`. `value` follows native dirty-value semantics (the `value` attribute is `defaultValue`). `src/internal/form-owner.ts` resolves the form owner in the fallback (shared with Button). `<aui-segmented>` renders `options` as a WAI-ARIA radiogroup with roving tabindex inside its shadow root and only submits when the value matches an option. The native `input` event is composed and crosses the shadow boundary as-is; `change` is not, so it is re-dispatched on the host — in both cases `value` is already updated. `<aui-field>` pushes its `label`/`description` into the slotted `<aui-input>`, `<aui-output>` or `<aui-segmented>`, which wire them up inside their own shadow roots (IDREFs can't cross shadow roots); verify such relations with `getAxNode` from `src/test-utils/ax.ts`. A component only registers the components it renders itself (field → icon-button), not the ones users slot into it.

**Shared internals** — `src/internal/` holds non-exported helpers shared across components: `spinner`, `inactive-click`, `form-owner`, `form-control`, `pausable-timer` (auto-close countdown with pause/resume that keeps the remaining time — WCAG 2.2.1; used by Alert's `timer` and Toast), `status-icons` (success/warning/error/info SVGs + state text shared by Output and Toast; inner shapes must use Lit's `svg` tag, an `html` template creates non-rendering HTML-namespace elements), and the overlay foundation for Modal/Alert/Toast/Drawer — `modal-dialog` (`ModalDialogElement`, the abstract base of `<aui-modal>` and `<aui-drawer>`: the whole `<dialog>.showModal()` open/close lifecycle, events, ESC/backdrop handling, initial focus and resource release; the shared `<dialog>` template is its `renderDialog({ prefix, panelClass, role })` and the shared styles are `dialogBaseStyles(prefix)` in `modal-dialog.styles.ts`, so a subclass only supplies a class prefix, its panel class and its own layout styles (`static styles = [dialogBaseStyles('x'), xStyles]`; backdrop / panel transitions and their reduced-motion overrides stay in the component's styles); a new subclass's tag must be added to its `DIALOG_HOSTS` so nested `[autofocus]` is skipped; it is one of the two internal modules whose `.d.ts` is published, via the exclude exception in `vite.config.ts`, because the public classes extend it — the other is `popup-trigger`, which `AuiButton` / `AuiIconButton` implement), `scroll-lock` (nested ref-count + scrollbar compensation), `focus-return` (deep `activeElement` through shadow roots), `top-layer` (`raisePopover`, a modal layer stack, and `followTopModal` which moves overlays such as the Toast viewport into the topmost modal's subtree, because a modal `<dialog>` makes everything outside it inert even when it is visually above). Page-global state lives on `globalThis` via `sharedState()` so multiple library copies agree. Browser-only imperative APIs must not throw `ReferenceError` during SSR (no `document`): `setTheme` returns early, `ToastService.show` returns an inert handle (`closed` already resolved), and `AlertService` returns a promise rejected with a "只能在瀏覽器端使用" error — not resolved as cancelled (server code would run the cancel branch) and not left pending (a route guard / resolver awaiting it would stall the SSR request); `pnpm verify:ssr` covers them. `<aui-modal>` is the reference user (all of the following lives in `ModalDialogElement`, so `<aui-drawer>` behaves the same): it intercepts the dialog `cancel` event (ESC) to run a cancelable `aui-hide` with `detail.reason` plus the exit transition, also listens to the native `close` event because Chrome force-closes on a repeated ESC without user activation, and exposes `MODAL_OVERLAY_SLOT` (`overlay`) inside its dialog for `followTopModal`. Its `close` event handler checks `dialog.open` rather than a flag, because `dialog.close()` dispatches `close` asynchronously and a modal reopened right away would otherwise be torn down by the stale event; an `[autofocus]` Lit element that has not rendered yet gets focus after its `updateComplete` (the panel is focused meanwhile). Removing an open modal from the page only takes the dialog out of the top layer (no `close` event, `open` stays set, so a reinserted modal would cover the page as a non-modal dialog): `disconnectedCallback` closes it and emits non-cancelable `aui-hide` / `aui-after-hide` (reason `api`, or the pending reason during the exit transition), which is also how a removed `<aui-alert>` reports `aui-cancel` and settles `AlertService`. `<aui-alert>` composes `<aui-modal>` (`dialog-role="alertdialog"`, `label` / `description` passed as text because its title and message live in another shadow root) and reports `aui-confirm` / `aui-cancel` after the modal's `aui-after-hide`; `AlertService` creates a one-off `<aui-alert>` on `<body>` per call, which also stacks above an open modal. `ToastService` is a page-wide singleton (`sharedState('toast@1')`) that owns the viewport — a plain `<div popover="manual" data-aui-toast-viewport>` with its own shadow styles, deliberately not a custom element so `verify:package`'s one-tag-per-entry check holds — plus the queue / max-visible, per-variant durations, the `placement` (six positions set via `ToastService.configure`, default `bottom-right`; written to the viewport as `data-placement`, whose styles pick the edge, the stacking direction — DOM order stays oldest-to-newest, top placements use `column-reverse` so the newest toast is nearest the edge — and the enter/exit offsets passed to `<aui-toast>` as inherited CSS custom properties; phones — width ≤ 480px, or landscape with height ≤ 480px — always use top-centre), hover/focus pause (re-checked by hit-testing the last pointer position after a removal, since `:hover` only updates on the next pointer move) and `raisePopover` + `followTopModal(viewport, { slot: MODAL_OVERLAY_SLOT })`. `<aui-toast>` renders an empty live region (`role="status"`, or `alert` for errors) and fills it two frames later so it is announced as a change; once in the viewport it may live inside a modal's shadow root, so tests must keep references instead of re-querying `document`. `src/internal/transition.ts` (`transitionTimeMs`) derives exit-animation timing from computed styles (Tooltip, Toast, and Modal/Drawer via `ModalDialogElement`). Call `pushModalLayer()` only after `dialog.showModal()` (and pop after `close()`); `followTopModal` records the element's home when it first moves into a modal and falls back to `<body>` if that home is gone, and tracks `beforetoggle` to reopen a popover whose modal was removed from the page (removal closes popovers without events); `raisePopover` re-raises open nested popovers too. Tests sit next to them (`src/internal/*.test.ts`).

**Code View** — `<aui-code-view>` keeps every line in the DOM (page find and multi-line selection work) and renders them in 200-line chunks with `content-visibility: auto` + `contain-intrinsic-block-size: auto calc(lines * 1lh)`. Because `content-visibility` always implies paint containment, the content wrapper gets a `min-width` estimated from the longest line in `ch` (`maxColumns` in `code-view/fold-ranges.ts`, which over-estimates on purpose: tabs, CJK and emoji count wide); otherwise long lines would be clipped and off-screen chunks would have zero width. Fold ranges come from indentation (`computeFoldRanges`, O(n), sorted by start line). Fold buttons use a roving tabindex. `checkVisibility({ contentVisibilityAuto: true })` reports on the skipped contents, so test a line inside a chunk, not the chunk itself.

**Navbar / Footer** — both switch to their narrow layout with a container query on their own width (Navbar < 768px, Footer < 640px), not the viewport; their hosts are `width: 100%` because inline-size containment makes the content width 0 inside flex / inline-block parents. `<aui-footer>` takes its columns as data (`columns` property) and fills the copyright year from the current date. `<aui-navbar>` is sticky on the host itself. Its menu button opens the element whose id is `menu-drawer` (duck-typed `show()`, no import of Drawer) and syncs `aria-expanded` from a document-level `aui-after-show` whose `composedPath()[0]` is that drawer plus an `aui-after-hide` listener on the open drawer itself (a drawer removed while open dispatches it while detached, so it never reaches `document`); since the drawer is modal, the navbar is inert while it is open, so the button only opens. The ⌘K / Ctrl+K listener is on `document` and is ignored while a modal that does not contain the navbar (checked across shadow roots) is open (`getTopModalLayer()`). The theme switch follows `<html data-theme>` through a `MutationObserver`.

**Tests** — run in real Chromium via web-test-runner with esbuild TS transform (Playwright's default `--hide-scrollbars` is disabled so scrollbar-dependent behaviour can be tested). A11y tests load `/dist/tokens.css` in a `<link>` so contrast checks use real tokens — **run `pnpm build` first** or color-contrast results will be wrong/missing. If a whole test file times out ("Browser tests did not finish") with 0 results, suspect a failing chai assertion that must print a Lit element (e.g. `expect(el).to.equal(other)` / `.to.be.instanceOf(...)`): formatting the diff can hang the browser. Compare first (`expect(a === b, 'msg').to.be.true`) to get a readable failure, and isolate blocks with `describe.only` / `it.only` (wtr only reports after the whole file finishes).

**Examples** — `examples/vue3`, `examples/angular` and `examples/react` (TASK-508) verify the custom elements work inside host frameworks (property/event binding, and two-way form binding: Vue `v-model` works as-is, Angular needs `ngDefaultControl` on `[(ngModel)]` / `[formControl]`, React 19 uses `value` + `onInput` with `event.currentTarget.value`; React 19 sets JSX props as element properties when the element has one, so arrays work, and listens to `aui-` events through `on<event-name>` props); they depend on the built `dist/`. `examples/react/src/type-tests/TemplateTypes.tsx` holds JSX type cases checked by `tsc` (`@ts-expect-error`); without the `@anchor-ui/core/react` reference every `aui-*` tag is an unknown intrinsic element, so the check still fails. React tests render with `react-dom/client` + `act` (`IS_REACT_ACT_ENVIRONMENT`), and because happy-dom does not retarget, React's delegated `onInput` is exercised by dispatching `input` on the host. They run on happy-dom, which has two gaps: it does not retarget events from shadow roots to the host (so IME-composition and `blur` behaviour that frameworks read from `event.target` is covered by the Chromium "framework binding contract" tests in `src/components/input/input.test.ts` instead), and zone.js cannot wrap its `MutationObserver` (its methods are non-enumerable), which `examples/angular/src/test-setup-happy-dom.ts` fixes before zone.js loads. Simulate typing by setting the inner `.control` value and dispatching a composed `input` event. Each example also has `tests/entries.spec.ts`, which imports only per-component entries (`@anchor-ui/core/field`, `/input`) and asserts which tags end up registered; it relies on Vitest's per-file isolation (a fresh environment and `customElements` registry per test file), so keep that isolation enabled.

## Conventions

- JSDoc on component classes uses the custom-elements-manifest tags (`@element`, `@slot`, `@csspart`, `@fires`); keep them updated when changing a component's API. `@fires` must carry the event type (`@fires {CustomEvent<FileDropDetail>} aui-file-drop - …`, `CustomEvent<null>` without detail, `Event` for native `input` / `change`): the framework type declarations are generated from it.
- Source comments and docs are mostly in Traditional Chinese; match the surrounding language.
- Font files are intentionally not bundled — only font-family tokens are defined (see README "載入字型"). The README is for consumers (intro, install, usage); developer docs — structure, scripts, yalc, release — live in `doc/development.md`.
