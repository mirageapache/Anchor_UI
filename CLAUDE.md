# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`@anchor-ui/core` — a framework-agnostic Web Component library built with Lit 3 + TypeScript, styled by SCSS design tokens exposed as CSS custom properties. Published as ESM-only. Elements use the `aui-` prefix (`<aui-button>`, `<aui-tooltip>`, …). Docs/specs live in `doc/` (written in Traditional Chinese): `anchor-ui-spec.md`, `design-system.md` (token dictionary), `anchor-ui-components-list.md` (20 planned components), `anchor-ui-development-schedule.md` (phases / TASK-xxx ids referenced in commit messages).

## Commands

Package manager is pnpm, pinned by `packageManager` in `package.json` (the single source for CI and the Docker script; workspace includes `examples/*`); Node version in `.nvmrc`. `playwright` is pinned to an exact version and must match the `mcr.microsoft.com/playwright:v<version>-noble` image in `ci.yml` — `pnpm check:versions` (run in the CI lint job) fails on drift.

- `pnpm storybook` — Storybook on :6006 (primary dev/preview surface); `pnpm dev` — plain Vite server
- `pnpm test:storybook` — Storybook 10 + `@storybook/addon-vitest`: `vitest run --project=storybook` (config in `vitest.config.ts`, which merges `vite.config.ts`; no prior build needed) turns every story into a Vitest browser-mode test in Playwright Chromium: a render smoke test for all of them plus the play functions (interaction scenarios live in `src/stories/Scenarios.stories.ts`; shadow-DOM helpers in `src/stories/play-utils.ts`, since Testing Library queries do not pierce shadow roots). The Playwright provider's `contextOptions` emulate reduced motion so overlay transitions are 0 ms; the browser API port is pinned to 6100 because Vitest's default (63315) sits in a range Windows/Hyper-V often reserves (`listen EACCES`). Play functions import from `storybook/test`, story types from `@storybook/web-components-vite`. CI runs it (then `build-storybook`) in the `storybook` job inside the Playwright image. Vitest here is only for stories — component tests stay on web-test-runner. Note `userEvent` (Testing Library) dispatches untrusted events: they do not trigger native `<dialog>` ESC handling, so close modals via their buttons in play functions.
- `pnpm build` — `tsc && vite build && pnpm build:tokens` → `dist/` (`index.js`, `.d.ts`, `styles.css`, `tokens.css`)
- `pnpm verify:package` / `pnpm size` — run after build (CI does both in the build job): tree-shaking / `exports` / `sideEffects` / published-files checks, and size-limit budgets per entry (`.size-limit.mjs`: gzip, `lit` ignored, limit = baseline + 10%)
- `pnpm typecheck`, `pnpm lint`, `pnpm stylelint`, `pnpm format:check` (these four are what CI runs before build; `:fix` / `format` variants exist)
- `pnpm test` — web-test-runner (Playwright Chromium) over `src/components/**/*.test.ts`, `src/internal/**/*.test.ts` and `src/*.test.ts` (e.g. `theme.test.ts`), excluding `*.visual.test.ts`
  - single file: `pnpm test --files src/components/button/button.test.ts` (or `pnpm wtr "<glob>"`)
  - `pnpm test:watch`, `pnpm test:coverage` (thresholds: 85% statements/functions/lines, 75% branches)
  - `pnpm test:a11y` — only `*.a11y.test.ts` (axe-core via `@open-wc/testing`'s `to.be.accessible()`)
  - `pnpm test:visual:docker` / `pnpm test:visual:docker:update` — visual regression (`*.visual.test.ts`, excluded from `pnpm test`) inside the official Playwright Docker image; baselines live in `screenshots/Chromium/baseline/` and must only be generated there (the visual config refuses to run outside Linux). Requires Docker. Shared setup (fonts via `@fontsource`, tokens, animation freezing) is `src/test-utils/visual.ts`; a new component should get a `<name>.visual.test.ts` declared with `describeVisual(title, cases)` (each case is shot in both themes). The `:update` run then calls `scripts/visual-baseline-diff.mjs`, which lists changed baselines and writes before/after/diff images to `screenshots/Chromium/changes/` (CI does the same on PRs against the target branch). Note the directory really is `Chromium` (capital C) — paths are case-sensitive on Linux/CI.
- `pnpm test:vue` / `pnpm test:angular` — integration tests in `examples/vue3` and `examples/angular` (vitest + happy-dom) that consume the library via `workspace:*`
- `pnpm typecheck:examples` / `pnpm build:examples` — `tsc` and production builds (Vue SFC compile, Angular AOT) of both examples against the built `dist/` (run `pnpm build` first); CI runs them in the test job. `build:examples` then runs `scripts/verify-example-builds.mjs`, which fails unless each example's output registers every component: a green `vite build` is not enough (`"noEmit": true` in the Angular `tsconfig.json` makes the AnalogJS plugin emit empty modules, so keep `--noEmit` on the command line instead)
- `pnpm smoke [vue3|angular] [--tarball <file>] [--keep]` — cross-framework smoke test (`scripts/smoke-test.mjs`, run `pnpm build` first): packs the tarball with `scripts/pack.mjs`, copies `smoke/<framework>` to a temp dir, `npm ci`, installs the tarball, type-checks (`vue-tsc` / `tsc`) and builds for production, then asserts the installed package (version, no install lifecycle scripts, no test files, every `exports` target exists, every bare import in `dist/` is a declared dependency) and the bundle (the app itself was compiled in, and only the imported entries are registered). A generated types-only file imports every entry so `skipLibCheck: false` covers all declarations. The `smoke/` projects are deliberately outside the pnpm workspace and do not list `@anchor-ui/core` in `package.json`; their dependencies are pinned by their own `package-lock.json`

Releases follow `doc/anchor-ui-release-guide.md` and are automated by release-please (TASK-405; `release-please-config.json` + `.release-please-manifest.json`, which must stay equal to `package.json` `version` — never bump the version, tag or create a Release by hand). `.github/workflows/release-please.yml` runs on every push to `main`: it opens/updates the single release PR (`chore(release): v<version>`, version + `CHANGELOG.md` computed from Conventional Commits; `always-update` rebuilds it on the latest `main`) and then dispatches `ci.yml` on the release PR branch via `workflow_dispatch`, because PRs updated with `GITHUB_TOKEN` trigger no `pull_request` runs and the `main` Ruleset needs its 7 checks (requires the repo setting "Allow GitHub Actions to create and approve pull requests"). Merging the release PR makes release-please tag the merge commit (lightweight tag via `force-tag-creation`) and create a **draft** Release, then call `.github/workflows/release.yml` (`workflow_call`, also `workflow_dispatch` with a `tag` input for reruns; tags created by `GITHUB_TOKEN` trigger nothing): it checks the tag is on `main`, waits for that commit's required checks (read from the `main` Ruleset by `scripts/wait-for-ci.mjs --sha`), runs `pnpm release:pack` with `RELEASE_TAG` (read by `scripts/verify-release.mjs` for the tag/version check; the tarball comes from `scripts/pack.mjs`, which packs a staged copy whose `package.json` has install lifecycle scripts such as `prepare: husky` removed), uploads the tarball and publishes the Release (prerelease when the version contains `-`). A final job merges `main` back into `develop`. `"prerelease": true` (versioning `prerelease`, type `beta`) produces `x.y.z-beta(.n)`; switching it to `false` graduates the next release to the stable version. `v0.3.0-beta` and earlier were released by hand with annotated tags.

**CI** (`.github/workflows/ci.yml`, PRs to `main` and `develop`, pushes on `main`, plus `workflow_dispatch` used for the release PR): the lint job (incl. `check:versions`, `release:verify --all-tags` and actionlint via the `rhysd/actionlint` Docker image — workflows can only really be exercised on GitHub, so lint them) gates the parallel `build`, `size-report`, `storybook`, `visual` and `test` jobs; `build` also packs the tarball and uploads it as an artifact for the `smoke` matrix job (`Framework Smoke Test (vue3)` / `Framework Smoke Test (angular)`, needs only Node + npm; both names must be in the `main` Ruleset to gate merges and releases); a final `CI Time Budget` job (`scripts/ci-time-report.mjs`, `actions: read`) writes per-job durations to the job summary and emits a warning (never a failure) when the run exceeds the 8-minute PR budget of TASK-214. Superseded PR runs are cancelled via `concurrency`. Required checks come from the `main` Ruleset and match job `name`s, so renaming a job means updating the Ruleset.

**Storybook preview** (`.github/workflows/storybook-preview.yml`, TASK-308): PRs to `main` build Storybook and deploy it to the `gh-pages` branch under `pr-preview/pr-<n>/`, then post or update one PR comment with the link (found by a hidden marker); closing the PR removes the directory (the `cleanup` job is triggered by `pull_request_target` so it also runs for conflicted PRs and executes `main`'s scripts, never PR code); pushes to `main` deploy to the site root and keep `pr-preview/`. The build job is read-only; only the `deploy` / `cleanup` jobs get `contents: write` + `pull-requests: write`, sparse-checkout just `scripts/pages-deploy.mjs`, `scripts/pr-preview-comment.mjs` and `.nvmrc`, and install nothing (the `deploy` job runs the PR branch's copy of those scripts, so a same-repo PR can rewrite `gh-pages` unreviewed). Fork PRs build but do not deploy (read-only token). Deploys are not serialized with `concurrency` (a group keeps only one pending run, so queued deploys or cleanups would be cancelled); `pages-deploy.mjs` re-clones and retries only when a push is rejected because the branch moved, and redacts credentials from git errors; the workflow-level group serializes runs per PR and keeps `main` deploys in order. Root deploys keep `pr-preview/` and `CNAME`. The preview comment is matched by marker and bot authorship. Both scripts are plain Node with tests next to them (`pnpm test:scripts`, `node --test` against a local bare repo and a fake API server; run in the CI lint job). GitHub Pages must be enabled once with source `gh-pages` / root (see `note/07-deployment.md` §6).

Commits are enforced by commitlint (Conventional Commits; types: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert) and Husky + lint-staged on pre-commit.

## Architecture

**Component layout** — each component is a folder `src/components/<name>/` with `<name>.ts` (LitElement class), `<name>.styles.ts` (`css` tagged template), `<name>.types.ts`, `index.ts` (re-exports class + types), `<name>.test.ts`, `<name>.a11y.test.ts`. A new component must also be exported from `src/components/index.ts` (which `src/index.ts` re-exports), get its `package.json` `exports` / `sideEffects` entries regenerated with `pnpm sync:package` (from `scripts/components.mjs`, the single source of the component list; the defining module must be named `<name>.ts`), a size baseline in `.size-limit.mjs` `BASELINES`, and gets a story in `src/stories/`. If it imports another component (e.g. icon-button → tooltip), add that edge to `ALLOWED_COMPONENT_DEPS` in `scripts/verify-package.mjs` — the tree-shaking check uses this explicit allow-list (not the source imports) and also inspects bundled modules, so undeclared cross-component code fails. `pnpm verify:package` and `pnpm size` fail if any of these are missing. Vite picks up the build entry automatically. Keep `"./src/**/*.ts"` in `sideEffects`: the field also applies to the library's own build, and without it bare registration imports such as `import '../tooltip/index.js'` get tree-shaken out of `dist/`.

**Tokens** — `src/tokens/*.scss` is the single source of truth (colors, typography, spacing, radius, motion). It is compiled two ways: into `dist/tokens.css` via `build:tokens` (sass), and also exposed as source SCSS through package exports (`./tokens`, `./reset`). Component styles reference tokens via `var(--space-lg, 24px)` with literal fallbacks; they never hardcode theme values.

**Theming** — dark mode is driven by `data-theme="dark"` on `<html>`. `setTheme` / `getTheme` / `toggleTheme` in `src/index.ts` manage it and briefly add a `.theme-transitioning` class for smooth transitions.

**Build** — Vite library mode, ESM-only with `preserveModules` (output mirrors `src/`): a full entry `src/index.ts` (registers every component) plus one entry per `src/components/*/index.ts`, exposed as `@anchor-ui/core/<name>` for tree-shakable on-demand imports. `lit*` and `@floating-ui/*` are externalized (`@floating-ui/dom` is a runtime dependency); test, story and `test-utils` files are excluded from the `.d.ts` output. `__PKG_VERSION__` is injected from `package.json` via Vite `define` (declared in `src/env.d.ts`). `@` aliases `src/`.

**Tooltip** is the most involved component: native Popover API (top layer) + `@floating-ui/dom` (`computePosition`/`autoUpdate`/flip/shift/arrow), emits cancelable `aui-show`/`aui-hide` and `aui-after-show`/`aui-after-hide` events. While open it sets `aria-describedby` on its target; for `<aui-button>` the focusable element is the inner `<button>`, so Button resolves its host `aria-describedby` and hands the elements over via `ariaDescribedByElements` (verify with `getAxNode` on the inner element). Custom events are prefixed `aui-`.

**Form controls** — `<aui-input>` and `<aui-segmented>` are form-associated custom elements sharing `src/internal/form-control.ts` (`FormControlController`: `attachInternals`, synchronous `setFormValue`, and the hidden-input + `reset`-listener fallback when `attachInternals` is missing, e.g. happy-dom). For `<aui-input>`: `setFormValue` runs synchronously on every value change, validity is mirrored from the inner native `<input>`/`<textarea>` (the single source of truth, incl. `setCustomValidity`) into `ElementInternals`, and it implements `formResetCallback` / `formDisabledCallback` / `formStateRestoreCallback`. `value` follows native dirty-value semantics (the `value` attribute is `defaultValue`). `src/internal/form-owner.ts` resolves the form owner in the fallback (shared with Button). `<aui-segmented>` renders `options` as a WAI-ARIA radiogroup with roving tabindex inside its shadow root and only submits when the value matches an option. The native `input` event is composed and crosses the shadow boundary as-is; `change` is not, so it is re-dispatched on the host — in both cases `value` is already updated. `<aui-field>` pushes its `label`/`description` into the slotted `<aui-input>`, `<aui-output>` or `<aui-segmented>`, which wire them up inside their own shadow roots (IDREFs can't cross shadow roots); verify such relations with `getAxNode` from `src/test-utils/ax.ts`. A component only registers the components it renders itself (field → icon-button), not the ones users slot into it.

**Shared internals** — `src/internal/` holds non-exported helpers shared across components: `spinner`, `inactive-click`, `form-owner`, `form-control`, `pausable-timer` (auto-close countdown with pause/resume that keeps the remaining time — WCAG 2.2.1; used by Alert's `timer` and Toast), `status-icons` (success/warning/error/info SVGs + state text shared by Output and Toast; inner shapes must use Lit's `svg` tag, an `html` template creates non-rendering HTML-namespace elements), and the overlay foundation for Modal/Alert/Toast/Drawer — `scroll-lock` (nested ref-count + scrollbar compensation), `focus-return` (deep `activeElement` through shadow roots), `top-layer` (`raisePopover`, a modal layer stack, and `followTopModal` which moves overlays such as the Toast viewport into the topmost modal's subtree, because a modal `<dialog>` makes everything outside it inert even when it is visually above). Page-global state lives on `globalThis` via `sharedState()` so multiple library copies agree. `<aui-modal>` is the reference user: it intercepts the dialog `cancel` event (ESC) to run a cancelable `aui-hide` with `detail.reason` plus the exit transition, also listens to the native `close` event because Chrome force-closes on a repeated ESC without user activation, and exposes `MODAL_OVERLAY_SLOT` (`overlay`) inside its dialog for `followTopModal`. Its `close` event handler checks `dialog.open` rather than a flag, because `dialog.close()` dispatches `close` asynchronously and a modal reopened right away would otherwise be torn down by the stale event; an `[autofocus]` Lit element that has not rendered yet gets focus after its `updateComplete` (the panel is focused meanwhile). Removing an open modal from the page only takes the dialog out of the top layer (no `close` event, `open` stays set, so a reinserted modal would cover the page as a non-modal dialog): `disconnectedCallback` closes it and emits non-cancelable `aui-hide` / `aui-after-hide` (reason `api`, or the pending reason during the exit transition), which is also how a removed `<aui-alert>` reports `aui-cancel` and settles `AlertService`. `<aui-alert>` composes `<aui-modal>` (`dialog-role="alertdialog"`, `label` / `description` passed as text because its title and message live in another shadow root) and reports `aui-confirm` / `aui-cancel` after the modal's `aui-after-hide`; `AlertService` creates a one-off `<aui-alert>` on `<body>` per call, which also stacks above an open modal. `ToastService` is a page-wide singleton (`sharedState('toast@1')`) that owns the viewport — a plain `<div popover="manual" data-aui-toast-viewport>` with its own shadow styles, deliberately not a custom element so `verify:package`'s one-tag-per-entry check holds — plus the queue / max-visible, per-variant durations, the `placement` (six positions set via `ToastService.configure`, default `bottom-right`; written to the viewport as `data-placement`, whose styles pick the edge, the stacking direction — DOM order stays oldest-to-newest, top placements use `column-reverse` so the newest toast is nearest the edge — and the enter/exit offsets passed to `<aui-toast>` as inherited CSS custom properties; phones — width ≤ 480px, or landscape with height ≤ 480px — always use top-centre), hover/focus pause (re-checked by hit-testing the last pointer position after a removal, since `:hover` only updates on the next pointer move) and `raisePopover` + `followTopModal(viewport, { slot: MODAL_OVERLAY_SLOT })`. `<aui-toast>` renders an empty live region (`role="status"`, or `alert` for errors) and fills it two frames later so it is announced as a change; once in the viewport it may live inside a modal's shadow root, so tests must keep references instead of re-querying `document`. `src/internal/transition.ts` (`transitionTimeMs`) derives exit-animation timing from computed styles (Tooltip and Modal). Call `pushModalLayer()` only after `dialog.showModal()` (and pop after `close()`); `followTopModal` records the element's home when it first moves into a modal and falls back to `<body>` if that home is gone, and tracks `beforetoggle` to reopen a popover whose modal was removed from the page (removal closes popovers without events); `raisePopover` re-raises open nested popovers too. Tests sit next to them (`src/internal/*.test.ts`).

**Tests** — run in real Chromium via web-test-runner with esbuild TS transform (Playwright's default `--hide-scrollbars` is disabled so scrollbar-dependent behaviour can be tested). A11y tests load `/dist/tokens.css` in a `<link>` so contrast checks use real tokens — **run `pnpm build` first** or color-contrast results will be wrong/missing. If a whole test file times out ("Browser tests did not finish") with 0 results, suspect a failing chai assertion that must print a Lit element (e.g. `expect(el).to.equal(other)` / `.to.be.instanceOf(...)`): formatting the diff can hang the browser. Compare first (`expect(a === b, 'msg').to.be.true`) to get a readable failure, and isolate blocks with `describe.only` / `it.only` (wtr only reports after the whole file finishes).

**Examples** — `examples/vue3` and `examples/angular` verify the custom elements work inside host frameworks (property/event binding, and two-way form binding: Vue `v-model` works as-is, Angular needs `ngDefaultControl` on `[(ngModel)]` / `[formControl]`); they depend on the built `dist/`. They run on happy-dom, which has two gaps: it does not retarget events from shadow roots to the host (so IME-composition and `blur` behaviour that frameworks read from `event.target` is covered by the Chromium "framework binding contract" tests in `src/components/input/input.test.ts` instead), and zone.js cannot wrap its `MutationObserver` (its methods are non-enumerable), which `examples/angular/src/test-setup-happy-dom.ts` fixes before zone.js loads. Simulate typing by setting the inner `.control` value and dispatching a composed `input` event. Each example also has `tests/entries.spec.ts`, which imports only per-component entries (`@anchor-ui/core/field`, `/input`) and asserts which tags end up registered; it relies on Vitest's per-file isolation (a fresh environment and `customElements` registry per test file), so keep that isolation enabled.

## Conventions

- JSDoc on component classes uses the custom-elements-manifest tags (`@element`, `@slot`, `@csspart`, `@fires`); keep them updated when changing a component's API.
- Source comments and docs are mostly in Traditional Chinese; match the surrounding language.
- Font files are intentionally not bundled — only font-family tokens are defined (see README "字體載入").
